# 工程规范（项目基线）

> 版本：v0.1　生效日期：2026-11-20
> 本文件是项目的行为约定。任何一条的修改都必须走「需求与计划」的变更记录。
> 违规不是"风格问题"，是需要回滚的缺陷。

---

## 1. 需求与计划必须可追踪

**规则**
- 所有需求、排期、范围变更，一律先写进 [`需求与计划.md`](./需求与计划.md)，再动代码。
- 每条需求有唯一编号（`REQ-xxx`），有状态（待排期 / 进行中 / 已完成 / 已取消）。
- 变更不是覆盖，是追加：保留原值 + 新值 + 原因 + 日期。

**落地**
| 场景 | 动作 |
|---|---|
| 新需求 | 在需求表新增一行，状态"待排期" |
| 调整范围 | 在变更记录表追加一行，写清"为什么" |
| 完成 | 状态改为"已完成"，填交付物路径 |

**校验点**：提交信息里引用了 `REQ-xxx`；`需求与计划.md` 的最后更新日期不早于代码提交日期。

---

## 2. 接口必须有契约文档

**规则**
- 前后端所有交互（HTTP / 反连协议 / 脚本 API）以 [`接口文档.md`](./接口文档.md) 为准，机器可读版本见 [`openapi.yaml`](./openapi.yaml)。
- **先改文档，再改实现**。文档与实现不一致时，以文档为准，实现算 bug。
- 每个接口必须写明：方法、路径、鉴权、请求体、成功响应、失败响应的错误码。

**落地**：新增/修改端点 → 同步更新 `接口文档.md` 与 `openapi.yaml` → 再改 `Commands.kt` / `hub.py`。

**校验点**：`scripts/check-api-doc.ps1`（待实现）比对代码里的路由常量与 openapi 路径集合。

---

## 3. 程序必须有日志管理

**规则**
- 统一入口：Android 用 `Logx`，PC 侧用 Python `logging`。**禁止裸用 `Log.d` / `print`**。
- TAG 规范：`MAE/<模块>`，模块名用大驼峰（`MAE/Engine`、`MAE/Shell`、`MAE/Server`）。
- 分级约定：
  | 级别 | 用途 |
  |---|---|
  | D | 调试细节，默认不输出 |
  | I | 生命周期、状态迁移（服务启动/停止、连接建立） |
  | W | 可恢复异常（重连、超时、降级） |
  | E | 功能失败（附异常栈） |
- 日志里**不得出现**：令牌、密码、完整个人信息、账号。
- PC 侧输出格式：`时间 级别 模块 消息`，可通过 `--log-level` 调整。

**校验点**：`grep -r "Log\.\(d\|i\|w\|e\)(" app/src` 应无结果（除 `Logx` 自身）。

---

## 4. 思考与输出使用中文

**规则**
- 代码注释、文档、提交信息、日志文案一律中文。
- 专有名词保留英文原样：`AccessibilityService`、`Shizuku`、`Gradle`、`token`、`selector`。
- 变量名/函数名用英文（遵循语言惯例），不强行拼音。

**例外**：协议字段、第三方 API 名称、错误码常量保持英文（如 `NOT_FOUND`、`hierarchy`）。

---

## 5. 必须考虑设备与系统兼容

**规则**
- 目标区间：**Android 11 (API 30) ~ 15 (API 35)**，见 [`兼容性矩阵.md`](./兼容性矩阵.md)。
- 任何用到 API 30 以上特性的地方，必须显式判断版本或用兼容实现。
- 涉及系统设置/权限差异的，必须给出降级路径（例如截图：`takeScreenshot` → `MediaProjection`）。
- 厂商差异（MIUI/HyperOS 无障碍门禁、后台限制）必须写进兼容性矩阵，并在 UI 上给出提示。

**校验点**：新增 API 调用时在 PR 描述里注明 `minSdk` 影响；`兼容性矩阵.md` 有对应行。

---

## 6. 功能变更与关键数据变更必须有单元测试

**规则**
- 触发条件（任一）：
  - 新增/修改接口
  - 选择器匹配、命令分发、序列化等纯逻辑
  - 数据结构变更（JSON 字段增删改）
  - 报告/客户端协议变更
- 测试位置：Android `engine/app/src/test/`，PC `tests/`。
- 覆盖率不设硬指标，但**上述触发范围内不允许零测试**。

**校验点**：`gradlew testDebugUnitTest` 与 `python -m unittest discover tests` 全绿才算可提交。

## 7. Git 版本管理

**规则**
- 提交信息格式：`<类型>(<范围>): <中文描述>`，类型取 `feat/fix/docs/refactor/test/chore`。
- 例：`feat(engine): 新增 findAll 与等待语义 (REQ-004)`
- 一个提交只做一件事；不提交编译产物、不提交本地配置。
- 分支：`main` 保持可用；功能分支 `feat/xxx`。

**校验点**：`git log --oneline` 可读；`git status` 干净。

## 9. 同步/推送前必须脱敏

**规则**
以下内容**永远不进入仓库**：

| 类别 | 示例 | 处理 |
|---|---|---|
| 令牌 | `<token>` | 代码/文档里只出现占位符 `<token>` |
| 个人路径 | `D:\<工作目录>\...`、`C:\Users\<user>` | 用环境变量或相对路径 |
| 设备信息 | 型号 `<设备型号>`、序列号、IP | 截图/日志里打码或替换 |
| 截图 | 含个人界面、聊天记录 | `reports/shots/` 整体 ignore |
| 邮箱/账号 | 真实邮箱 | 用 `noreply` 地址 |

**流程**
1. 推送前跑 `python scripts/desensitize.py`
2. 脚本报 `BLOCK` 必须处理后才能提交；CI 每次推送都会跑同一套规则
3. 首次 `git init` 前也要跑一次（历史无法轻易改写）

**校验点**：脚本退出码为 0。
